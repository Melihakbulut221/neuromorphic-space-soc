# TTIHP26b pilot: die content, pin contract, tile budget and submission

Design record for the ROADMAP phase P1 pilot. It states what is on the
die, what each pin does, how much silicon the design actually needs
against the Tiny Tapeout tile grid, what the conditional SRAM upgrade
would cost, and what the submission tree contains.

Convention, as everywhere in this repository: **[fact]** = measured in
this environment or read out of an installed file; **[estimate]** =
derived or judged. Every area number below names the PDK it came from.

RTL: `hw/rtl/pilot_top.v` (integration) and
`hw/rtl/tt_um_melihakbulut_nssoc.v` (Tiny Tapeout wrapper). That wrapper
was called `tt_um_pilot.v` while most of this record was written, and
section 8.4 item 2 called for the rename; it has since landed, together
with the deletion of the generated name adapter. The rename moved no
logic, so every area, cell and flip-flop figure below survives it and is
quoted under the current name. `tt_um_pilot` appears below only where it
names a file inside a retained run directory, or where the rename itself
is the subject.

Verification: `hw/tb/test_pilot_top.py`, run by
`hw/tb/Makefile.pilot`. Submission: `tt/`, generated by
`scripts/gen_tt_submission.py`, guarded by
`sw/tests/test_tt_submission.py`.

## 0. Headline

**The tile shape is 4x2 = 8 tiles (~EUR 560), and the submission tree is
built at that shape.**

This is no longer a projection. The design has been taken through the
complete `Classic` flow at 4x2 locally, against the submission's own
configuration, and it closes to a GDS: **69.52 % utilization, zero
detailed-route DRC errors, zero Magic DRC errors, zero Netgen LVS
errors, zero antenna violations, and zero setup, hold, max-cap and
max-slew violations across all three timing corners** **[fact, section
5.3]**. The five submission tests passed on the post-route netlist of a
superseded harden; that check has **not** been re-run against the
current one (section 5.4).

**The shape survives; the margin does not.** 69.52 % is where the design
landed after the `lif_core` memory hardening, against 60.91 % before it,
and at the 70 % planning criterion this record uses that leaves **0.68 %
of the 4x2 core spare** where the previous run left 12.99 % **[estimate,
section 4 head]**. 4x2 is still the right shape and it is still the shape
the submission tree is built at. It is no longer a shape with room in it,
and the timing margin went the same way: the slow corner closes at
+0.403 ns, down from +6.436 ns (section 4.6).

**The tile budget is open, and by a hair.** The run those figures come
from is dated 2026-08-27 00:03; `hw/rtl/pilot_top.v` was rewritten at
00:17 to give the third TMR replica an XOR mixing transform, which costs
**+0.92 %** of synthesis area measured here — more than the 0.68 % that
was left. A re-harden against the current RTL is running. Until it
lands, treat this document's areas and margins as the best measurement
available and not as the answer; the *shape* does not turn on it, only
whether the 70 % planning criterion is still met inside it. Section 4
opens with the detail.

The default 2x2 pilot of docs/06 section B.6 does not fit, and the
margin is not close. The placed design is **180,651 um2** of standard
cells **[fact]**. A 2x2 block offers **126,685 um2** of placement rows —
measured, not interpolated, from the `tt_block_2x2_pgvdd.def` template
the flow actually uses. That is **142.6 %**: not a tight fit but an
impossible one. No 2x2 run was attempted — the number applies this
design's *measured* placed area to the 2x2 row count, so the 142.6 % is
an **[estimate]** built on a fact rather than on another estimate, and
the error runs the wrong way for 2x2: a denser floorplan makes the
resizer work harder, not less. The floor is firmer still — the
pre-placement synthesis netlist alone, 146,310 um2, is **115.5 %** of a
2x2 before a single timing-repair buffer exists, and the flow inserted
30,805 um2 of them.

Every area, utilization and timing figure in this record now comes from
the memory-hardening re-harden
`hw/openlane/pilot_ihp/runs/ihp-memecc/` (2026-08-27 00:03), not from
the superseded `tt/runs/tmr-reharden/` or `tt/runs/tt-harden/`. Section
4 opens with what that run measured and what it cost.

This does not change the funding envelope. docs/06 section B.6 already
carries EUR 560 for the 8-tile option. What changes is the meaning of
the 2026-09-07 go/no-go, which stops being *how many tiles to buy* and
becomes *whether the SRAM macro goes into the tiles we are buying
anyway* — and section 6 shows that the macro variant is a 12-tile
design, not an 8-tile one.

## 1. What is on the die

Every block instantiated by `pilot_top.v` was already verified before it
was integrated. The pilot adds glue, not arithmetic.

| Block | Source | Configuration | Prior verification |
|---|---|---|---|
| LIF datapath | `hw/rtl/lif_core.v` | 8 neurons x 8 axons, 4-bit signed weights in flip-flops | 24 cocotb tests: lockstep against `sw/golden/lif_core.py` for the arithmetic, plus a directed group on the command and handshake interface that the golden model cannot represent at all; SymbiYosys `formal/lif_ctrl.sby`, 8 tasks, all PASS (docs/11 sections 1.1 and 6.2) |
| Input event queue | `hw/rtl/aer_fifo.v` | 16 bits x 4 entries | 11 cocotb tests; SymbiYosys `prove`, `prove_d4`, `bmc`, `cover` all PASS |
| Output event queue | `hw/rtl/aer_fifo.v` | 16 bits x 4 entries | as above |
| Configuration voter | `hw/rtl/tmr_voter.v` | 55-bit voted word | 7 cocotb tests, of which 6 execute and 1 is width-gated at each of three widths; SymbiYosys `prove`, `bmc`, `bmc_abc`, `bmc_w1`, `bmc_w32`, `cover`, `cover_w1`, `cover_w32` all PASS |
| Weight-word codec | `hw/rtl/secded_enc.v`, `hw/rtl/secded_dec.v` | (72, 64) Hsiao | 12 cocotb tests; `bmc`, `bmc_abc`, `cover` PASS |
| Register subset, serial host port, event dispatcher, ECC-checked weight loader, fault counters | `hw/rtl/pilot_top.v` | see section 3 | 23 cocotb tests, this pilot suite |
| Tiny Tapeout wrapper | `hw/rtl/tt_um_melihakbulut_nssoc.v` | pin map, uio directions, reset synchronizer; also the submission top level, so it is copied verbatim into `tt/src/` | same suite, which drives the TT port list, plus 5 cocotb tests in `tt/test` that drive it as the top level |

Storage on the die, at the 8 x 8 default: 256 synapse bits, 160 neuron
state bits (16-bit V + 4-bit R per neuron), 128 event-queue bits, and a
72-bit ECC-protected weight staging word, plus the `wchk` and `smem`
check fields the `lif_core` memory hardening added. The wrapper declares
**1,241 flip-flops** **[fact, `sw/tests/test_synthesis_guards.py`'s own
declared-census recipe, re-measured 2026-08-27]** and **1,235** map
through the Tiny Tapeout flow, all `sg13g2_dfrbpq_1` **[fact,
`hw/openlane/pilot_ihp/runs/ihp-memecc/06-yosys-synthesis/reports/stat.json`]**;
the six-flop gap is ordinary optimisation of declared-but-constant or
unused state, and it is the same six as before the hardening. The
figures before that hardening were 1,161 declared and 1,155 mapped; the
pre-TMR-fix netlist carried 1,037, which is the merge section 4.2
records. The note at the head of section 4 decomposes the +80.

Three things the pilot deliberately does **not** carry, each with its
reason:

- **No SRAM macro.** That is the ROADMAP default. The 2026-09-07
  go/no-go decided whether it changes, and it is already answerable:
  `docs/12-sg13g2-flow-bringup.md` sections 7 and 8 hardened one
  `RM_IHPSG13_1P_512x32_c2_bm_bist` and the recommendation is **NO-GO**
  for TTIHP26b — the macro places, routes and closes timing but fails
  Magic DRC, KLayout DRC and Netgen LVS on causes that are entirely
  inside the vendor views. See section 6 below.
- **No management core.** A SERV-class RV32 is in the docs/06 B.6
  8-tile option; the pilot is driven from the host serial port instead,
  which is what a bring-up board does anyway.
- **No runtime CFG_NEUR.** `lif_core` has no active-neuron count by
  design — implementing one would be RTL with no golden reference (see
  that file's header). CFG_NEUR reports the elaborated geometry.

### 1.1 What the fault-tolerance demonstrators actually demonstrate

Both demonstrators sit on the real datapath, not beside it.

**SECDED.** The 64-bit weight word that software writes through
`W_DATA_LO` / `W_DATA_HI` *is* the data field of a physically stored
(72, 64) codeword. On commit the check field is computed, the armed
`ECC_INJ` pattern is XORed into the stored codeword, the decoder runs,
and the weight loader writes 16 weights into `lif_core` **from the
decoder output** — so a corrected single-bit upset never reaches the
datapath, and an uncorrectable word contributes zero (E10, docs/10
section 11.2). The injected error survives in the stored word, so a
bench can re-check it with the `SCRUB_STB` pin as often as it likes;
with `CTRL.SCRUB_EN` set, each check writes the repaired word back. The
pilot register `ECC_INJ_POS` moves the injected bit anywhere in the
72-bit codeword, so the full syndrome space is walkable on silicon.

**TMR.** Every configuration bit that reaches `lif_core` — THETA,
V_RESET, S_LEAK, S_SYN, T_REFR, the flag bits and PASS_TILE_OFF, 55 bits
in total — is held in three replicas and voted by `tmr_voter` before it
leaves the register block. `TMR_INJ` holds one bit of one replica wrong.
Software still reads the voted value; the inference still produces
exactly the same spike stream; `CNT_TMR` and the TMR pin still record
that it happened, which is the docs/08 section 2.3 rule that a silently
repaired upset must reach telemetry. The suite proves the masking by
running the same inference clean and corrupted and requiring identical
output.

The replicas survive synthesis, which is not automatic and was checked
rather than assumed — see section 4.2.

Honest limit: the injector drives the replica's read path, not its
storage flop, so the pilot implements no replica resynchronization. That
is consistent with `tmr_voter.v`'s own contract, which leaves
resynchronization to the protected block; here a configuration rewrite
restores all three replicas.

## 2. Pin contract

Fixed Tiny Tapeout budget: 8 dedicated inputs, 8 dedicated outputs, 8
bidirectionals, plus clock and reset from the infrastructure (docs/06
section B.2). All 24 are assigned; one input is reserved.

This table, the header of `hw/rtl/tt_um_melihakbulut_nssoc.v` and
`tt/info.yaml` must agree.
`sw/tests/test_tt_submission.py::test_pinout_matches_the_wrapper_header`
enforces the second pair mechanically.

### 2.1 Dedicated inputs (`ui_in`)

| Pin | Name | Function |
|---|---|---|
| ui[0] | SER_SCK | Serial clock, mode 0 (CPOL 0, CPHA 0), max clk/4 |
| ui[1] | SER_CS_N | Frame select, active low |
| ui[2] | SER_MOSI | Serial data in, MSB first |
| ui[3] | AER_IN_STB | External AER event strobe, rising-edge triggered |
| ui[4] | AER_IN_TICK | 0 = SPIKE at AER_IN_ADDR, 1 = TICK |
| ui[5] | AER_OUT_ACK | External AER consumer acknowledge, rising-edge |
| ui[6] | SCRUB_STB | ECC re-check / scrub pulse, rising-edge triggered |
| ui[7] | reserved | Tie low |

### 2.2 Dedicated outputs (`uo_out`)

| Pin | Name | Function |
|---|---|---|
| uo[0] | SER_MISO | Serial data out, MSB first |
| uo[1] | BUSY | STATUS.BUSY |
| uo[2] | AER_IN_RDY | The input queue has room for one more event |
| uo[3] | AER_OUT_VLD | An event id is presented on AER_OUT_ID |
| uo[4] | ERR | Sticky STATUS.ERR_CFG or STATUS.OVF_SEEN |
| uo[5] | SEC | Sticky: at least one single-bit ECC error corrected |
| uo[6] | DED | Sticky STATUS.DED_SEEN |
| uo[7] | TMR | Sticky: the configuration voter masked a disagreement |

Four of the eight outputs are fault pins. That is deliberate: it makes
every hardening event visible on an oscilloscope with no host software,
which is what a radiation-effects bench needs. All four clear through
`STATUS_CLR` or `FAULT_CLR`.

This record originally carried a known gap here: `lif_core` exposes
`err_cfg`, the level output it latches when its Hamming-distance-2 state
register decodes to an illegal value and the FSM parks in `S_SAFE`, and
`pilot_top` left that port unconnected, so an upset in the datapath's
own control FSM reached neither `STATUS.ERR_CFG` nor the ERR pin.
Verilator named it as `PINMISSING` in the Tiny Tapeout lint step, and
section 8.4 item 1 asked for the fix.

**The gap is closed.** `pilot_top.v` connects the port and section 7 of
that file states the resulting semantics: `err_cfg` is ORed into
`STATUS.ERR_CFG` live, so a `STATUS_CLR` cannot report a still-parked
core as recovered, and it is latched into the sticky bit as well, so
`CTRL.SOFT_RST` — the recovery for this fault — does not erase the
evidence that an upset happened. Both halves are covered by
`hw/tb/test_pilot_top.py`, and the live half needed a test written
specifically for it (docs/11 section 6.2 records why the obvious one did
not distinguish it). The `PINMISSING` warning is gone with it
(section 5.2).

### 2.3 Bidirectionals (`uio`)

Directions are fixed at elaboration; `uio_oe` is the constant `0xF0`.

| Pin | Direction | Name | Function |
|---|---|---|---|
| uio[3:0] | input | AER_IN_ADDR | Axon id for the strobed event (N_AXONS <= 16) |
| uio[7:4] | output | AER_OUT_ID | Emitted neuron id (N_NEURONS <= 16) |

The full 16-bit event word of docs/10 section 7.1 is always readable
over the serial `EVQ_OUT` register; the uio nibble is the low four bits
of its ID field, for a consumer that wants the event stream without a
host.

### 2.4 Host obligations

Three, and all three are real. They are stated in `pilot_top.v` section
2, reproduced in `tt/docs/info.md`, and held by the test suite at their
boundary values.

1. `SER_SCK <= clk/4`. The serial port lives entirely in the `clk`
   domain behind two-flop synchronizers.
2. `SER_CS_N` falls at least one full `SER_SCK` period before the first
   `SER_SCK` edge. This is the trap recorded in the sibling project's
   shipped submission and it applies here for the same reason.
3. `SER_CS_N` stays high at least one full `SER_SCK` period **between**
   frames. Found during this pilot's bring-up: the bit counter is held
   at zero only while the synchronized select reads inactive, so a
   deselect that is never seen leaves the counter running and the next
   frame decodes at the wrong offset.

Frame format: 40 `SER_SCK` cycles, command byte `{WR, ADDR[6:0]}` then
32 data bits, MSB first. `ADDR[6:0]` is the `regmap/regmap.yaml` byte
offset shifted right by two.

## 3. Register subset

Implemented from `regmap/regmap.yaml` (docs/10 section 10), addresses
and reset values taken from the generated `hw/rtl/npu_regs.vh`, never
hand-copied:

`ID`, `VERSION`, `SCRATCH`, `CTRL`, `STATUS`, `STATUS_CLR`, `CFG_NEUR`,
`CFG_AXON`, `CFG_THRESH`, `CFG_VRESET`, `CFG_LEAK`, `CFG_SYNSHIFT`,
`CFG_REFR`, `CFG_FLAGS`, `PASS_TILE_OFF`, `W_ADDR`, `W_DATA_LO`,
`W_DATA_HI`, `N_ADDR`, `N_DATA`, `CNT_SEC`, `CNT_DED`, `CNT_EVQ_OVF`,
`CNT_AXON_OOR`, `FAULT_ADDR`, `ECC_INJ`, `FAULT_CLR`, `EVQ_STAT`,
`EVQ_IN`, `EVQ_OUT`, `NODE_ID`.

Not implemented: `W_BASE` and `PASS_ID`, both multi-pass sequencer
bookkeeping with no hardware effect in a single-pass build.

The same list, with offsets and access codes, is rendered into the
submission datasheet `tt/docs/info.md` directly from
`sw/golden/regmap_gen.py`, so the datasheet cannot drift from the
register map; `sw/tests/test_tt_submission.py` re-checks every offset it
finds in that file against `ADDR`.

Documented deviations, each with its cost or its reason:

| Id | Deviation | Reason |
|---|---|---|
| D1 | Fault counters are 8 bits and saturate, not 32 | Four 32-bit counters cost about 11,000 um2 on `sg13g2` [estimate], to count events a pilot reads every few seconds. At 4x2 the area argument no longer binds; keeping D1 is now a schedule decision, not a budget one (section 6) |
| D2 | `CFG_NEUR` is read-only and reports the geometry | `lif_core` has no runtime active-neuron count and no golden reference for one; `CFG_AXON` is fully writable and does drive the docs/10 section 6 drop rule |
| D3 | `W_ADDR` is a weight-word index, not a byte address | One 16-weight word per commit; auto-increments on `W_DATA_HI` exactly as the register map specifies |
| D4 | `W_DATA_LO`/`W_DATA_HI` read back the *stored* ECC data field | They are the physical data field, so an injected upset is visible until it is scrubbed. That is the demonstrator |
| D5 | Three pilot-only registers at 0x0A0, 0x0A4, 0x0A8 | `ECC_INJ_POS`, `TMR_INJ`, `CNT_TMR`; they sit in the unmapped region of the same window and do not change the register-map contract |

1. **The tile-budget headroom is spent.** The core did not move — 259,837 um2 of

   180,651 / 0.70 = **258,073 um2** of rows against the 259,837 um2 the
   4x2 core offers. That is **0.68 % spare**, where `tmr-reharden` left
   12.99 % **[estimate, arithmetic on measured areas]**. **The pilot
   still fits 4x2 and its shape has not changed** — but there is no

   hardening, which is a slow-corner Fmax of **51.0 MHz** against the
   50 MHz the design declares **[estimate, arithmetic on a measured
   slack]**. Section 4.6 states it as what it is.
3. **The hardening itself is intact.** The configuration TMR survived
   synthesis: **55 flip-flops under each of `u_cfg_a`, `u_cfg_b` and
   `u_cfg_c`** in the final netlist, and
   `design__instance_unmapped__count: 0` **[fact,

   counters, antenna 0 nets / 0 pins, detailed-route DRC 0 (section 5.3).

**And then the tree moved again, fourteen minutes later, exactly as it
did after `tmr-reharden`.** `hw/rtl/pilot_top.v` was rewritten at
**2026-08-27 00:17**, against `ihp-memecc`'s 00:03 **[fact, file

**That is why the tile budget is open rather than closed.** +0.92 % of
synthesis area against **0.68 % of spare** is not a rounding difference;
it is larger than the margin. Carried through the place-and-route growth
this design shows, 180,651 x 1.0092 = 182,304 um2 placed, which needs

criterion is now a coin toss for this design rather than a margin, and
only a full re-harden settles it. **One is running against the current
RTL as this is written; when it lands, every figure in this section is
requoted from it.** The direction is not in doubt: `MIX` adds area and

**CORRECTION (2026-08-26): the replicas did NOT survive synthesis, and
the check below could not have detected it.** This section originally
concluded that the TMR survived, on the reasoning preserved verbatim
underneath. That conclusion was wrong, and the way it was wrong is worth
keeping: the experiment could not distinguish its two hypotheses.

The netlist that fed the 4x2 harden contains 362 references to `cfg_a`
and none to `cfg_b` or `cfg_c` **[fact]**. `opt_dff` normalises the three
banks into identical enable flops and `opt_merge` then hashes them into
one, so the voter read a single physical bank three times: an upset would
have corrupted all three "replicas" together and the voter would have
agreed with itself. The fix (commit `e45d52d`) makes each replica a
`keep_hierarchy` `pilot_cfg_bank` instance carrying a per-replica storage
polarity.

**The polarity alone was never enough for three banks, and this record
said otherwise twice before getting it right.** The first revision of
this paragraph claimed the polarity "is plain Verilog and depends on no
attribute"; the second corrected that to "**replica C depends on
`keep_hierarchy`**". The first was false and `docs/20` section 3.3
measured it: strip the attribute, leave the polarities exactly as
designed, and the mapped count is **1,100, not 1,155** — exactly one
bank, 55 flip-flops, lost, with the design sitting on the guard's
`lost <= TMR_W` bound rather than comfortably inside it **[fact,
`docs/20` section 3.3]**. A storage bit has two polarities and three
replicas cannot be given three distinct ones, so no choice of
`CFG_POL_C` improves it. The second was true when written.

**It is no longer true, and the reason is a change to the RTL rather
than a change of mind.** `hw/rtl/pilot_top.v` (rewritten 2026-08-27
00:17) gives replica C a per-replica storage *transform* that is not a
polarity: with `MIX = 1`, `u_cfg_c` stores an invertible XOR mixing of
the configuration word, so every one of its 55 stored bits is an XOR of
two or three distinct configuration bits. Nothing of the form
`x_i ^ x_j (^ x_k)` equals `x_i` or `~x_i`, so no per-bit structural hash
can match replica C against A or B — that is a proof about the
construction, not a measurement, and the measurement agrees: strip
`keep_hierarchy` now and **all 1,155 flip-flops survive with no loss at
all**, in the ASIC flow and in `synth_ecp5` alike **[fact,
`hw/rtl/pilot_top.v` header section 9 item (e); `docs/20` sections 11.3
and 11.4]**. So **replica C no longer depends on `keep_hierarchy`**, and
the guard's `lost <= TMR_W` bound is now met with `lost = 0` rather than
`lost = 55`.

One candidate that looks equivalent and is not, kept because it is the
mistake a reader would make: a per-replica bit **rotation**.
`cfg[(i+k) % 55]` is neither `cfg[i]` nor its inverse, so it appears to
give a third function — but structural hashing matches on a flip-flop's
(D, EN, reset) signature, not on bit position, so a rotation relabels
which cell holds which bit and leaves the *set* of stored functions
unchanged. Measured, replica C rotated by 7 with `keep_hierarchy`
stripped: **1,100 flip-flops, identical to polarity alone** **[fact,
`docs/20` section 11.2]**.

`deferred_flatten` is still required, but for a different reason and a
weaker one: parameterising the bank makes yosys derive `$paramod` module
types, and `Checker.YosysUnmappedCells` counts any `$` cell type as
unmapped, so under the LibreLane default (`flatten`) the run aborts
before it can produce a netlist at all. That is a flow-mechanics
dependency, not a hardening one. With the attribute present, mapped
flip-flops go from 1,045 to 1,155 in both the ASIC and the ECP5 flow,
with exactly 55 flops under each replica — and `ihp-memecc` reproduces
that per-replica count at 1,235 total after the memory hardening
(section 4 head).

Why the original check read as confirmation: adding `(* keep *)` left the
count unchanged, and that was interpreted as "nothing was merged". The
same observation is equally consistent with "the merge happened and
`(* keep *)` does not prevent it" — which is what was actually true.
`(* keep *)` preserves the *names*, filling the netlist with
`assign cfg_b[3] = cfg_a[3]` aliases while the flip-flops stay merged
**[fact, measured during the repair]**. A null result was read as a
positive one. The lesson is now enforced mechanically rather than by
care: `sw/tests/test_synthesis_guards.py` counts flip-flop *cells* under
each replica instance in the real hardened netlist, and fails on three
separate mutations of the fix.

The original reasoning, retained as the record of the error:

> `cfg_a`, `cfg_b` and `cfg_c` are 55-bit registers with identical D
> inputs, identical enables and identical reset values, which is exactly
> the shape a logic optimizer merges. Two independent checks:
>
> - Local Yosys 0.33, `synth -flatten`: 1,036 `sg13g2_dfrbpq_1`. Marking
>   all three replicas `(* keep *)` and re-synthesizing: 1,036. Identical,
>   so nothing was merged — Yosys `opt_merge` does not merge flip-flops
>   unless asked with `-share_all`.
> - The Tiny Tapeout flow, Yosys 0.67, default `SYNTH_HIERARCHY_MODE`
>   (`flatten`): 1,037 `sg13g2_dfrbpq_1`, sequential area 50,801 um2.
>
> A merge would have cost 110 flip-flops and would not have shown up in
> simulation at all, because the injector drives the read path.

The last sentence was correct and is the reason this went unnoticed for
as long as it did: fault injection at RTL level cannot see a structure
that synthesis removed.

**Superseded by the same correction.** This paragraph originally
explained why the submission did *not* need the sibling project's
`SYNTH_HIERARCHY_MODE: deferred_flatten` setting: the argument was that
this project had no `keep_hierarchy` attribute anywhere in `hw/rtl`, so
the setting would protect nothing. That was true when written and is
false now. The TMR repair builds each replica as a `keep_hierarchy`
`pilot_cfg_bank` instance, which puts this project in exactly the
situation the workaround exists for — under the LibreLane default
(`flatten`) the `$paramod` module types survive into techmap and
`Checker.YosysUnmappedCells` aborts the run. Both `tt/src/config.json`
and `hw/openlane/pilot_sky130/config.json` now carry
`SYNTH_HIERARCHY_MODE: deferred_flatten`, and `scripts/gen_tt_submission.py`
emits it. The sibling project reached the same setting by the same route,
which is a mild argument that the route is the natural one for TMR built
this way.

146,310 um2 / 7.26 um2 per `sg13g2_nand2_1` = **20,153 gate
equivalents** **[estimate]**. At that document's 4.3 kGE raw per IHP tile
that is 4.7 tiles; at its 2.5-3 kGE practical per tile it is **6.7-8.1

### 4.4 Why 2x2 fails, in one number

`tt_um_melihakbulut_nssoc` at 8 x 8 is 105,452 um2 post-techmap;
`lif_core` at 8 x 8 alone is 43,512 um2 measured standalone. The
difference — **61,940 um2** — is the register bank, the serial host
port, the event queues, the dispatcher, the ECC-checked weight loader,
the TMR domain, the SECDED codec and the fault counters.

A 2x2 block at a realistic 70 % utilization holds 126,685 x 0.70 /
1.2907 = **68,700 um2** of post-techmap cells, where 1.2907 is the
pre-fix tool delta and place-and-route growth together (136,107 /
105,452). This whole subsection is stated in pre-fix, local Yosys 0.33
terms, because those are the measurements it rests on and they were not
re-made (section 4.1). The TMR fix and the `lif_core` memory hardening
each move every figure in it the same way, upward — together they took
the measured placed area from 136,107 um2 to 180,651 um2, +32.7 % — so
they make the 2x2 case worse rather than better and the conclusion is
unaffected **[estimate on the direction and on the +32.7 %; the pre-fix
numbers are fact]**.

So the observability and hardening set consumes **90 % of a 2x2 block
before a single neuron is instantiated**. There is no geometry that
rescues it: the smallest configuration the design will elaborate at all
(4 neurons x 8 axons, 32 synapses) still needs 88.3 % utilization in
2x2.

Stripping content does not rescue it either. Deleting both
demonstrators and one event queue recovers, from measured pieces: the
SECDED codec 6,865 um2, the 55-bit voter 2,895 um2, one `aer_fifo`
7,182 um2, and both injection position decoders 6,170 um2 — that last
figure measured by stubbing the two one-hot decoders out and
re-synthesizing, 105,129 um2 against 98,959 um2 in the same pair of runs
**[fact]**. That is 23,112 um2 measured. Add the 72-bit ECC staging word
and the 110 redundant configuration replica bits, 182 flip-flops at the
measured 48.99 um2 per `sg13g2_dfrbpq_1` plus an 18.14 um2 write mux,
about 12,200 um2 **[estimate]**, and the total recovered is roughly
35,300 um2, leaving about 70,150 um2 — which still needs 71.5 %
utilization in 2x2. A 2x2 submission would therefore have to delete the
fault tolerance and still be marginal, which removes the pilot's reason
to exist: the docs/06 WP5 case is that this chip is the cheapest
instrument for first TID/SEE data on `sg13g2_stdcell` logic, and that
argument needs the counters.

Getting there took one non-obvious step, and it is worth writing down
because it presents as a broken design.

With stock Icarus Verilog 12.0 the same run gives **1 of 5**. Every
register reads back zero and the ready pin is low out of reset. The
cause is not the netlist: the `ihp-sg13g2` standard-cell models drive
their outputs from `delayed_D`, `delayed_CLK` and `delayed_RESET_B`,
which are the negative-timing-check outputs of `$setuphold` and
`$recrem`. Icarus does not implement those and says so, once per cell:

    warning: Timing checks are not supported and delayed signal
    "delayed_CLK" will not be driven.

An undriven `delayed_CLK` leaves every `sg13g2_dfrbpq_1` output at `x`
for the whole simulation. Proof rather than assertion: driving the
delayed signals from their undelayed sources in a scratch copy of
`sg13g2_stdcell.v`, changing nothing else and using the same netlist and
the same testbench, takes the run from 1/5 to 5/5 **[fact]**.

Tiny Tapeout's `gl_test` action does not hit this: it installs
`TinyTapeout/iverilog` v13.0 rather than a distribution build. So CI is
fine and a developer running `make GATES=yes` on a laptop is not. The
note is carried in `tt/test/README.md` so that it travels with the
submission.

## 6. The SRAM upgrade, and why it is a 12-tile design

docs/06 section B.6 offers a conditional upgrade to 4x2 = 8 tiles
carrying one `RM_IHPSG13` SRAM macro under BIST, gated on the
2026-09-07 go/no-go in section B.6.1. Section 4.3 changes the shape of
that decision.

**The tile count is no longer what the gate decides.** 4x2 is what the
flip-flop pilot needs anyway. The gate now decides content, and the
budget line in docs/06 (~EUR 560) is unchanged for the flip-flop
variant.

What the macro would add, if it passes:

- **Synapse capacity.** `RM_IHPSG13_1P_512x32` holds 16 kbit = 4,096
  four-bit synapses, against 64 in the flip-flop pilot — a factor of 64.
- **A real memory ECC path.** The pilot's SECDED codec is a staging-word
  demonstrator: one codeword, checked on commit and on a scrub pulse.
  With a macro it becomes what docs/10 section 5 actually specifies — a
  72-bit physical word per 16 weights, decoded on every read, with the
  scrubber walking the array while the input queue is empty. E10 would
  then be a property of the read path rather than of the load path.
- **BIST.** 25 of the 27 installed macros expose a second `A_BIST_*`
  port set (docs/12 section 6.1). Exercising it on silicon is directly
  reusable in the full SoC.
- **Full-width counters.** D1 exists because of the 2x2 budget; at 8 or
  more tiles the four fault counters can go back to their 32-bit
  register-map width.

What it costs, measured against the section 4.3 geometry:

`RM_IHPSG13_1P_512x32_c2_bm_bist.lef` declares `SIZE 416.64 BY 191.34`
**[fact, installed PDK]** = 79,720 um2. With the LibreLane default 10 um
macro halo on each side it reserves 436.64 x 211.34 = **92,280 um2**
**[fact for the macro, estimate for the halo]**. The logic measures
180,651 um2 of placed cells **[fact, section 4.1]**, i.e. 258,073 um2 of
rows at 70 % utilization. Total **350,353 um2** **[estimate]**.

| Shape | Tiles | Rows (um2) | Macro + logic fits? |
|---|---|---|---|
| 4x2 | 8 | 259,837 | **no** — needs 134.8 % of the rows |
| 6x2 | 12 | 392,988 | yes, 10.8 % spare |
| 3x4 | 12 | 443,784 | yes, 21.1 % spare |

Each hardening step has widened the gap rather than closing it: 4x2
needed 110.3 % of the rows before the TMR fix, 122.5 % after it and
**134.8 %** after the memory hardening, while the 12-tile margins fell
from 27/35 % spare to 19/28 % and now to **10.8/28 %** — read 6x2's
10.8 % as the one to watch, because it is the shape Tiny Tapeout's
template comment certainly sells (section 6 below on 3x4).

Two things this arithmetic does not capture, and both make the macro
variant harder rather than easier. First, the logic would grow again: a
memory ECC read path and a scrubber are new RTL, and the `lif_core`
memory hardening is the *load-path* half of that, already measured
above — the read-path half is not in any of these numbers. Second, a
macro changes the resizer's job, so the 1.2347 growth factor measured on
an all-standard-cell floorplan is not transferable to a floorplan with a
92,280 um2 obstacle in it.

**The 8-tile SRAM pilot as described in docs/06 B.6 does not fit.** It
needs 12 tiles (~EUR 840), or the logic content has to be cut.

Which 12-tile shape is not a free choice, and there are two separate
constraints:

- *Floorplan.* A 6x2 block is 313.74 um tall. The macro with its halo is
  211.34 um tall, which leaves a 102.4 um strip — about 27 standard-cell
  rows — above or below it. That is placeable but awkward, and it puts
  the macro's 188 bottom-edge signal pins close to the block boundary.
  A 3x4 block is 710.64 um tall and leaves a full 499 um. On floorplan
  grounds 3x4 is the better 12 tiles.
- *Availability.* `tt-support-tools` `tech/ihp-sg13g2/tile_sizes.yaml`
  carries 3x4, and `project_info.py` validates `tiles` against that
  file, so a 3x4 `info.yaml` passes the local check **[fact]**. But the
  template's own `info.yaml` comment lists the valid set as "1x1, 1x2,
  2x2, 3x2, 4x2, 6x2 or 8x2" — no four-row shape **[fact,
  ttihp-verilog-template `6598bef4`]**. The two disagree, and the
  submission app is the authority. **Confirm with Tiny Tapeout before
  planning on 3x4**; if only two-row shapes are sold for TTIHP26b, the
  12-tile option is 6x2 and the floorplan constraint above becomes real.

That was a finding for the 2026-09-07 gate rather than a blocker for it,
and the gate's own experiment has since been run. `docs/12` sections 7
and 8 hardened a registered wrapper around one
`RM_IHPSG13_1P_512x32_c2_bm_bist`: detailed routing into the 188
bottom-edge Metal2 pins **converged with zero DRC errors and zero
antenna violations**, and timing closed at 50 MHz — the pin-access risk
below did not materialise. Signoff did not close: Magic DRC and KLayout
DRC both report errors that are 100 % inside the vendor macro geometry,
and Netgen LVS fails on CDL-versus-GDS hierarchy naming (IHP-Open-PDK
issue #239) plus a bus-delimiter mismatch. Both blocking causes are
upstream of this repository, so the 12-tile conversation is **not**
worth having for TTIHP26b; docs/12 section 8 recommends NO-GO and
docs/06 B.6.1 now carries that status against the gate.

One caveat on quoting that run as a tile-shape result: it was
floorplanned at `0 0 854.40 340.20`, the interpolated 4x2 block, not the
measured `0 0 854.40 313.74` of section 4.3. The macro and its halo
still fit the real block, so the DRC/LVS/routing conclusions stand, but
the die was 8.4 % larger than the shape it stood in for (docs/12
section 6.5).

Two risks docs/12 section 6.4 quantifies stay attached to any macro
option, and the routed run has now separated them. **188** signal pins
crowded onto the bottom edge on Metal2 with one 0.26 um access point
each, spanning x = 3.29 to 413.35 of a 416.64 um macro **[fact,
installed PDK LEF]**, was called the most likely place a routed run
fails — and it was **not**: the router converged in four iterations with
no pin-access tuning. The LVS path the PDK does not pre-arrange, with
CDL and GDS hierarchy names that disagree, is the one that actually
failed.

## 7. Decision

1. **Submit at 4x2 = 8 tiles (~EUR 560).** The design has been run
   through the whole flow at that shape and closes at **69.52 %**
   utilization with zero DRC errors, zero antenna violations and zero
   timing violations on three corners. That is not a projection. **What
   it no longer leaves is margin**: 0.68 % of the core is spare against
   the 70 % planning criterion, down from 12.99 % after the TMR fix and
   25.2 % before it, and the `MIX` change already in the tree is larger
   than what remains (section 4 head). The shape is not in doubt — 4x2
   is what the design needs and no smaller shape is close — but for a
   PDK whose open views are still described upstream as a pre-production
   preview (docs/12 section 2.2), submitting with a fraction of a percent
   in hand is a different proposition from submitting with thirteen. The
   re-harden now running against the current RTL is what settles whether
   the 70 % criterion is still met; the *shape* it will report is 4x2
   either way.
2. **3x2 = 6 tiles is not the floor, it is a gamble.** It needs
   **93.5 %**, far above every reference point this project has, and it
   would start global placement at **75.7 %** against the template's
   default target density of 60 — over the target before placement
   begins. At 4x2 the same mechanism has already produced a `GPL-0302`
   warning that the flow absorbed on its own (section 4.3); at 3x2 it
   would not be absorbable. The EUR 140 saved buys a floorplan problem
   two weeks before a shuttle close.
3. **Do not attempt 2x2.** It is **42.6 %** over on measured placed
   area, at a utilization no design in or near this project achieves, and
   stripping it to fit deletes the fault tolerance that justifies the
   run.
4. **Fold the finding into docs/06 sections B.6 and B.6.1.** The default
   content line ("16-32 LIF neuron crossbar" in 2x2) does not survive
   contact with the measured register bank and demonstrators; the honest
   default is 8 neurons x 8 axons in 8 tiles, and 16 neurons needs 12.
   **Done** — docs/06 B.6 now carries the 4x2 = 8-tile flip-flop-RAM
   pilot as the default, records the 2x2 line as superseded with the
   then-current 107.4 % figure, and prices the SRAM-macro variant at 12
   tiles. That figure is now **142.6 %** (section 4.3); docs/06 has not
   been re-edited for it and the conclusion does not turn on it.
5. **Keep the 2026-09-07 gate, and re-scope it.** It no longer chooses
   the tile count. It chooses whether the tiles being bought hold a
   flip-flop synapse file or an SRAM macro — and section 6 says the
   macro option is a 12-tile design, not an 8-tile one. **Done, and the
   re-scoped gate is already answerable**: docs/06 B.6.1 now words it as
   a macro-content decision with three conditions, and condition 1 fails
   on the docs/12 section 7 evidence. The flip-flop-RAM pilot is what
   ships.

## 8. The submission tree

### 8.1 What exists

`tt/` is a port of the Tiny Tapeout Verilog template, at 4x2, with this
project's RTL in it. Provenance, recorded rather than assumed:

- template: `https://github.com/TinyTapeout/ttihp-verilog-template`,
  commit `6598bef4d3159f19fe471a2a2225df52e6f5ad25` ("chore: update tags
  for TTIHP26b", 2026-07-27);
- schema and tile geometry: `tt-support-tools` commit `01d5d281`
  (2026-08-20), which is the `main` branch the TTIHP26b GDS action
  installs.

Contents: `info.yaml`, `docs/info.md`, `src/` (the RTL plus the
template's `config.json`), `test/` (Makefile, `tb.v`, a self-contained
cocotb suite), the four GitHub workflows, the dev container, the VS Code
settings, `README.md`, `LICENSE.PENDING.md` and `MANIFEST.sha256`.

### 8.2 It is generated, not maintained

`scripts/gen_tt_submission.py` builds the whole tree. The RTL under
`tt/src` is a byte-for-byte copy of `hw/rtl`; the datasheet's register
table is rendered from `sw/golden/regmap_gen.py`; the scaffolding is
carried as literals tagged with the upstream commit they came from.
`--diff-template` re-fetches the template and proves, file by file, that
everything claimed to be verbatim really is — 11 files, all verbatim,
plus two more (`.gitignore` and `test/README.md`) whose upstream base is
byte-identical and which the generator only appends to **[fact,
2026-08-25]**. It also names the six files that are rewritten rather
than copied, so a re-port knows exactly what needs human eyes.

`sw/tests/test_tt_submission.py` is the guard, and it checks the tree
three independent ways: `MANIFEST.sha256` against the files, `tt/src`
against `hw/rtl`, and the whole tree against a fresh in-memory
regeneration. A hand edit to one copied RTL file trips all three
**[fact, verified by planting one]**. If it fails after an intentional
RTL change, the fix is `python3 scripts/gen_tt_submission.py`, never an
edit under `tt/`.

### 8.3 The top-level module name

The submission's top level is `tt_um_melihakbulut_nssoc`, not
`tt_um_pilot`. `tt-support-tools` `configure.py` asserts that macro
instance names are unique across the whole shuttle, and `tt_um_pilot` is
generic enough that a collision would be found at shuttle assembly —
late, and by someone else.

While this record was being written, `tt/src/tt_um_melihakbulut_nssoc.v`
was a generated name adapter: it instantiated `tt_um_pilot` and
connected the eight ports straight through, with no logic and no state,
so that `hw/rtl` could be copied verbatim. Synthesis flattened it away.

That is no longer the shape. **`hw/rtl/tt_um_pilot.v` has been renamed
to `hw/rtl/tt_um_melihakbulut_nssoc.v`, the adapter is deleted, and the
submission carries one file and one hierarchy level less** — the change
section 8.4 item 2 asked for. Nothing else about the pin contract or the
hardened logic moved with it, which is why the area and flip-flop
figures above still hold; `hw/rtl/tt_um_melihakbulut_nssoc.v`'s header
records the old name so a reader of an old run directory can follow it.

### 8.4 Changes asked for in files this record did not own — both done

Two were listed, both in `hw/rtl`, neither blocking. Both have since
landed. They are kept here rather than deleted because the sections
above cite them and because what the first one cost is the useful part.

1. **`pilot_top.v`: connect `lif_core`'s `err_cfg`. DONE.** `lif_core`
   latches that output when its Hamming-distance-2 state register
   decodes to an illegal value and the FSM parks in `S_SAFE` — which is
   exactly the single-event-upset signature this chip exists to measure.
   `pilot_top` left the port unconnected (Verilator `PINMISSING`), so
   `STATUS.ERR_CFG` reported only a locked-write attempt and an invalid
   configuration, never an FSM upset, and the ERR pin never lit for one.
   It is now connected, ORed into `STATUS.ERR_CFG` live *and* latched
   into the sticky bit, with the reasoning in `pilot_top.v` section 7.
   That closes the fault-visibility gap against the docs/08 section 2.3
   convention.

   This record also predicted that a test "needs a formal or
   force-based stimulus, so the honest alternative is to document the
   limitation instead". The prediction was half right and the half it
   got wrong is worth recording. A **deposit** into the state register
   is enough for the stimulus — no force needed — and
   `hw/tb/test_pilot_top.py` does exactly that. But a force *was* needed
   for something this record did not anticipate: the live and latched
   halves of `STATUS.ERR_CFG` are not separable from the pins at all,
   because the latch re-arms every cycle while the core is parked. The
   first test therefore passed just as happily with the live term
   deleted. Closing that took a second test built around the one clock
   cycle in which the ERR pin is high and the sticky flop is not, plus a
   forced clear of the sticky flop. docs/11 section 6.2 carries the
   general form of the lesson: a wire being connected, and the
   connection being tested, are two claims and the first does not imply
   the second.
2. **`tt_um_pilot.v`: rename the module. DONE.** Renamed to
   `tt_um_melihakbulut_nssoc`. `ADAPTER_NAME` is gone from
   `scripts/gen_tt_submission.py` and the tree is regenerated; the
   submission lost one file and one hierarchy level and nothing else
   changed. Section 8.3 has the detail.

### 8.5 What was run here, and what is left

Which RTL these numbers belong to: `hw/rtl` entered version control in
commit `be6ebd9`, so the coarse anchor is the commit itself and the fine
one is `tt/MANIFEST.sha256`, which carries a SHA-256 for every copied
source and therefore also catches an uncommitted working-tree edit that
a commit hash cannot. The flow results below were produced from that
tree; an `hw/rtl` edit that changes any of those hashes invalidates them
and `sw/tests/test_tt_submission.py` will say so. The check that matters
after such an edit is a re-run of `-T Yosys.Synthesis`: if the cell area
and the flip-flop count are unchanged, the place-and-route numbers still
hold. That check was exercised twice here: `hw/rtl/lif_core.v` was
edited by another workstream mid-session on two separate occasions, and
a re-synthesis after each returned exactly 107,781.8616 um2, 6,587 cells
and 1,037 flip-flops — the same netlist to the last cell **[fact,
against the pre-fix `be6ebd9` tree; those three figures are the record of
that check and are superseded as a description of the design, see section
4.1]**. The cocotb suites that instantiate it (`Makefile.lif`,
`Makefile.pilot`) and the submission's own suite were re-run after each
edit and stayed green **[fact]**.

**The same check has since fired in the other direction, twice, and both
times fourteen minutes after a harden finished.** The first: run 3
(`tmr-reharden`) synthesised commit `fe89f0d`, `hw/rtl/lif_core.v` was
rewritten fourteen minutes later, and the re-synthesis returned **1,235
flip-flops, not 1,155** **[fact, re-measured 2026-08-26]**. That was
answered by run 4. The second: run 4 (`ihp-memecc`) finished at 00:03 on
2026-08-27, `hw/rtl/pilot_top.v` was rewritten at 00:17 to give replica C
the `MIX` storage transform, and the re-synthesis returns **147,648.69
um2 against the run's 146,309.97, +0.92 %, with the flip-flop count
unchanged at 1,235** **[fact, run tags `memecc-synthcheck` and
`memecc-synthcheck3`, both returning the same figure to the last digit]**.

Note which half of the check fired each time. The `lif_core` case moved
the flip-flop count and the `MIX` case did not; the rule is a
conjunction, so **either** half failing invalidates the place-and-route
numbers, and this record has now seen one of each. The section 4 head
carries what the second one costs and why the tile budget is open rather
than closed because of it. A re-harden against the current RTL is
running.

**Two observations for whoever owns the wave, because this is now a
pattern and not an accident.** Both invalidations arrived within fifteen
minutes of a multi-hour harden completing, from workstreams that had no
way to know one was in flight. A harden of this design costs about
thirty-two minutes wall clock — run 4 ran 23:32:01 to 00:03:59 **[fact,
step-directory mtimes]** — so the fix is not to work more carefully but
to stop starting hardens against a tree that other sessions are still
writing to, or to pin the sources into the run tag. Until that changes,
every figure in section 4 should be read with its run tag and its
