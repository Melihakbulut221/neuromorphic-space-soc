# 25 — sky130A at twelve tiles: the cross-PDK claim re-measured, and what the slow-corner miss actually is

Status: complete. Four sky130A hardens at 6x2, all four reaching a GDS
with every sign-off deck at zero. This document supersedes nothing
outright. It reproduces `docs/23` section 5 independently, closes
`docs/23` open item 6, and replaces the *cause* `docs/18` section 3.3b
gives for the sky130 slow-corner miss with a three-term decomposition in
which `docs/18`'s term is the second largest and the largest term is not
in `docs/18` at all.

**No document other than this one is edited here.** Section 10 lists the
lines in `docs/18` and `docs/22` that should change, with replacement
text, and leaves them to whoever owns those files.

Convention, inherited from `docs/18`: **[fact]** = measured in this
environment or read out of an installed file; **[estimate]** = derived
or judged; **[planned]** = an intention with no artifact.

Run trees under `hw/openlane/*/runs/` are **gitignored**, so every number
below is quoted with the run tag and the step directory it came from.

### Headline

- **The question this work was given had already been answered, and the
  answer holds.** The brief was posed as though sky130 6x2 had not been
  run. `docs/23` section 5 had run it — `sky-09-6x2`, clean on every
  deck. This document re-ran it as `sky-11-6x2` from an independently
  pinned snapshot and got a **byte-identical layout**: same MD5 on the
  output DEF at detailed placement, CTS, post-CTS timing repair, global
  routing and antenna repair, the same detailed-route trace, and the same
  post-route slack on all nine corners to four decimal places
  **[fact]**. Section 4.2. So the result is reproduced rather than
  re-quoted, and the rest of the document does the part that was open.
- **It routes, and it is nowhere near the 4x2 divergence.**
  **55.8841 % placement utilization**, global-route overflow **0**
  against 4x2's **22,357**, worst layer **met1 59.84 %** against 4x2's
  **met1 133.91 %**, and detailed routing converging monotonically to
  zero in three passes of sixteen iterations from a peak of **6,998**
  violations — where 4x2 *rose* through 218,483, 348,149 and 364,603 and
  was stopped. Sections 3 and 4.
- **Sign-off is clean on every deck, on all four runs.** Magic DRC 0,
  KLayout DRC 0, Magic/KLayout XOR 0, all seven Netgen LVS counters 0,
  antenna 0 nets / 0 pins, detailed-route DRC 0,
  `flow__errors__count` 0. Section 3.
- **`PNR_CORNERS` is inert at twelve tiles, and the proof is tighter than
  at 4x2.** The identical DEF enters the detailed router in both arms —
  placement, clock tree, every resizer, global routing and antenna repair
  are bit-for-bit unaffected **[fact]**. The slow corner ends **0.0912 ns
  worse**, -7.3966 against -7.3054, for **+10 um2 of placed area
  (+0.008 %)**. Sections 6.2 and 6.3.
- **`docs/18`'s diagnosis is incomplete, and the missing term is now the
  largest one.** `docs/18` section 3.3b says the post-CTS resizer "closed
  the slow corner outright" on its own estimate and that the whole miss
  is created afterwards, by the parasitic model. That was true of
  `sky-04-tmr`. On this netlist the post-CTS resizer enters at
  **-13.545 ns**, leaves at **-4.672 ns** with **219 of 220 endpoints
  still violating**, and logs
  `[WARNING RSZ-0062] Unable to repair all setup violations` **[fact]**.
  The 7.3054 ns miss is **4.672 ns of timing the flow could not repair
  even on a model that flatters it**, **2.246 ns of parasitic-model gap**
  and **0.387 ns of interconnect corner**. Section 7.
- **The parasitic-model term is not a per-unit-RC problem, and this was
  tested rather than argued.** `docs/20` section 6.3 ranked "populate
  `LAYERS_RC` for sky130A" first among the untried fixes and
  `SIGNAL_WIRE_RC_LAYERS` second. Both were run here. Giving
  place-and-route a per-corner `LAYERS_RC` built from the PDK's own three
  tech LEFs moves the corner by **+0.0007 ns**. Adding a signal wire
  model **2.03x** more resistive and non-zero via resistance moves it
  **0.1138 ns the wrong way**. The model-gap term itself stays at
  **2.215 to 2.312 ns across all four runs** **[fact]**. Sections 8
  and 8.2.
- **The sky130A LibreLane PDK ships neither `LAYERS_RC` nor `VIAS_R`;
  ihp-sg13g2 ships both, and maps one tech LEF onto all three corner
  prefixes where sky130A maps three.** That is the concrete form of
  `docs/18`'s "parasitic-model gap": a **PDK-integration difference, not
  a process difference**. Section 7.3.
- **Cross-PDK portability: restored for manufacturability at twelve
  tiles, lost for timing, and the timing half is now understood rather
  than merely observed.** Section 9.

## 2. The question, and the fact that it was already answered

The brief for this work was posed as open: sky130 stopped routing at 4x2
(`docs/22` section 5), the design has since moved to 6x2, so does it
route at the new shape?

**It had already been run.** `docs/23` section 5 hardened sky130A at both
twelve-tile shapes — `sky-09-6x2` and `sky-10-3x4` — end to end, and
reported both clean on every deck. Both run directories are on disk and
their `final/metrics.json` reproduce the numbers `docs/23` prints.

This is stated plainly rather than worked around, for two reasons. Re-running
a settled experiment and presenting it as new is how a repository
accumulates duplicate evidence that later disagrees with itself. And the
thing that *was* open is narrower and more useful: `docs/23` section 10
item 6 records that "`docs/18` section 6's `PNR_CORNERS` hypothesis was
never re-tested at twelve tiles", and a routed design is the
precondition for testing it.

So this document does two things. It reproduces the 6x2 harden
independently, which turns a single-run routing result into a repeated
one (section 4.2). And it then runs the experiments nobody had run
(sections 6 to 8).

## 4. Routing behaviour, against the 4x2 divergence

This is the part the brief asked to be reported iteration by iteration,
and it is the part that decides whether the design can be built on
sky130 at all.

### 4.1 Global routing: the leading indicator

Every config in this repository sets `GRT_ALLOW_CONGESTION`, inherited
from the Tiny Tapeout defaults, so global routing does not fail on
overflow — it reports it and hands the result to the detailed router.
Overflow is a leading indicator, not an error.

| | sky130 4x2 `sky-08-ptrtmr` | **sky130 6x2 `sky-11-6x2`** | IHP 6x2 `shape-6x2` |
|---|---|---|---|
| Total resource | 86,645 | **134,772** | 315,588 |
| Total demand | 95,569 | **60,337** | 63,482 |
| **Total usage** | **110.30 %** | **44.77 %** | 20.12 % |
| **Total overflow** | **22,357** | **0** | **0** |
| met1 | **133.91 %** (10,752 overflow) | **59.84 %** (0) | — |
| met2 | 99.85 % (2,787) | 52.68 % (0) | — |
| met3 | 124.18 % (7,870) | 35.49 % (0) | — |
| met4 | 61.33 % (948) | 8.74 % (0) | — |

**[fact, `hw/openlane/route_trace.py` on each run's `GRT-0096` final
congestion table]**

The 4x2 column is what a congestion failure looks like: demand exceeding
supply on met1 by a third and on met3 by a quarter, 22,357 grid cells of
overflow handed to the detailed router before it starts. The 6x2 column
has **no overflow on any layer** and its worst layer sits at 59.84 %.
These are not two points on a spectrum. The difference is the
denominator: the sky130A 6x2 core offers **225,802 um2** against 4x2's
**149,183 um2**, for a design needing about 126,000 um2 of cells.

### 5.2 `design__violations` is still 0, and this is still a trap

227 setup violations at each of the three `ss` corners and 1,811
max-slew violations at `max_ss`, and the run finishes with
`design__violations: 0` and `flow__errors__count: 0` **[fact]**. That is
not a suppression this configuration applied: the PDK ships
`TIMING_VIOLATION_CORNERS: ["*tt*"]`, so the setup checker only looks at
the three `tt` corners where the count is 0, and
`MAX_SLEW_VIOLATION_CORNERS: [""]` is LibreLane's match-nothing wildcard,
so the max-slew checker is disabled outright **[fact,
`sky-11-6x2/resolved.json`]**.

`docs/18` section 3.3a established this at 4x2. It reproduces unchanged
at 6x2 and on a design whose miss is now 7.3 ns rather than 3.0 ns.
**A green LibreLane run is not a statement that timing closed.**

**The shape of the problem has inverted.** On `sky-04-tmr`, 100 % of the

the flow tried to fix, on a model that flatters it, and failed.

durable part of that finding. The interconnect-corner term is the

flow setting was going to reverse it.** The growth is not the flow
getting worse; it is two waves of hardening — the `lif_core` SECDED
memories and the AER pointer TMR, 1,155 flip-flops to 1,275 and
80,069 um2 of synthesis area to 99,876 — pushing the critical path past
what the resizer can repair at 20 ns on `sky130_fd_sc_hd` at
`ss_100C_1v60`. The critical endpoint is `u_pilot.u_lif._3663_/D` in
every one of the four runs **[fact]**.

### 7.3 Why the model is optimistic, in three named mechanisms

`docs/18` says only that `LAYERS_RC` is null. The run prints exactly what
the flow used, in `14-openroad-dumprcvalues`, and it is more specific.

**(a) Place-and-route never loads the `max` technology.** sky130A ships
three tech LEFs and LibreLane maps them onto the corner prefixes:

```
TECH_LEFS = {"nom_*": …/sky130_fd_sc_hd__nom.tlef,
             "min_*": …/sky130_fd_sc_hd__min.tlef,
             "max_*": …/sky130_fd_sc_hd__max.tlef}
```

But OpenROAD's database holds exactly one technology. Across all 76
step directories of `sky-11-6x2` only three read a tech LEF at all —
`13-openroad-floorplan`, `14-openroad-dumprcvalues` and
`54-openroad-rcx` — and only `54-openroad-rcx` reads more than one
**[fact, `Reading technology LEF file at` lines]**. Every PnR step's own
`_env.tcl` carries `set ::env(TECH_LEF) …__nom.tlef` beside the
three-entry `TECH_LEFS` **[fact]**. Floorplan reads `__nom`, later steps
inherit it through the ODB, and the `__max` LEF first appears at
extraction — after the last step that could act on it.

This is the deeper reason section 6's result is structural: **there is no
`max` interconnect model inside place-and-route for a corner list to
select.**

For contrast, `ihp-sg13g2` maps the *same single* tech LEF onto all three
prefixes and ships only a `nom_*` OpenRCX ruleset **[fact,
`shape-6x2/resolved.json`]**, so its PnR estimate and its extraction
cannot disagree about interconnect in this way.

**(b) The wire estimate is a flat average over layers the design does not
use evenly.** `14-openroad-dumprcvalues/resizer_values_after.rpt`, units
`resistance 1kohm`, `capacitance 1pF`, `distance 1um`:

```
==== Estimation RC Values ====
Signal   Avg   4.402703e-04   8.148294e-05
Clock    Avg   4.402703e-04   8.148294e-05
```

against the per-layer values in `tlef_values.rpt` — met1 and met2 at
`8.928571e-04`, met3 and met4 at `1.566667e-04`, a **5.70x** ratio
**[fact]**. The 6x2 detailed route puts **190,189 um on met1 and
159,961 um on met2** against **75,808 um on met3 and 6,454 um on met4**,
so **81.0 %** of routed length is on the two resistive layers **[fact,
`Total wire length on LAYER` lines in `44-openroad-detailedrouting`]**.
Weighting the per-layer resistances by that usage gives **7.528e-04**,
**1.71x** the estimate the optimizer worked from **[estimate, arithmetic
on measured quantities]**.

**(c) Via resistance is modelled as exactly zero.** The same report:

```
==== Via R Values ====
licon 0.000000e+00   mcon 0.000000e+00   via 0.000000e+00
via2  0.000000e+00   via3 0.000000e+00
```

while the tech LEF declares `mcon 9.30`, `via 4.50`, `via2 3.41`,
`via3 3.41`, and the `__max` LEF declares `mcon 23.0`, `via 15.0`,
`via2 8.0`, `via3 8.0` **[fact]**. The 6x2 route contains **76,686
vias** **[fact]**, and `RCX_MERGE_VIA_WIRE_RES` is `true`, so extraction
charges every one of them and place-and-route charges none. The
`Rt. Layer RC Values` table in the baseline is **entirely zero** as well
— the resizer has no per-routing-layer model at all, only the single
averaged wire figure **[fact]**.

**The single-sentence version.** `ihp-sg13g2` ships `LAYERS_RC` *and*
`VIAS_R` in its `libs.tech/librelane/config.tcl`; **sky130A ships
neither**, and both resolve to `null` in every run in this repository
**[fact, `resolved.json`]**. `docs/18`'s "parasitic-model gap" is a
**PDK-integration difference, not a process difference** — which is a
materially different thing to tell a reader asking whether the *design*
ports.

## 8. Testing the parasitic-model diagnosis directly

Section 7.2's middle row is derived by subtraction, so it is worth
testing against a run rather than left as arithmetic. `docs/20`

**Restored for manufacturability at twelve tiles. Lost for timing, and
the timing half is now understood rather than merely observed.** The two
halves have different evidence and different consequences and have to be
stated separately.

**Manufacturability: restored, on stronger evidence than `docs/18` ever

hardens whose layouts are byte-identical**; and it survives **four

**The tile-count caveat is load-bearing and must travel with the

that is not expected to change, because the sky130A 4x2 core offers
149,183 um2 against IHP's 259,837 for a design needing about
126,000 um2 of cells. **The honest form of the claim is "portable at
twelve tiles", not "portable".**

**Timing: not restored, and it will not be restored by a flow setting.**

remaining 4.7 ns is the design not making 20 ns at that corner on
`sky130_fd_sc_hd`.** No corner list, no repair step and no parasitic
model recovers that part, and sections 6 and 8 are four runs

## 11. Two repository items found on the way

Neither is in this workstream's files and neither is fixed here.

**`hw/openlane/pin_rtl.py` cannot pin a config that carries a nested
dictionary.** It re-reads the base config with
`json.load(..., object_pairs_hook=list)` to preserve the duplicate `//`
comment keys the Tiny Tapeout config relies on, then re-serialises. That
hook applies at **every** nesting level, so a value that is itself a
dict — `LAYERS_RC`, `VIAS_R`, `TECH_LEFS` — is written out as a list of
`[key, value]` pairs and LibreLane rejects it:

```
ERROR  Tcl-style flat dictionary provided for variable 'LAYERS_RC' is
       invalid: uneven number of components (3)
```

**[fact, reproduced; both runs of section 8 failed this way on the first
attempt]**. It has never bitten before because no config in this
repository had a nested value. The fix is to apply the hook only at the
top level. The runs here worked around it by restoring the two keys from
the source config after pinning, **in the disposable snapshot only**;
`pin_rtl.py` is untouched and section 12 shows the workaround.

**`VIAS_R` corner wildcards do not work in LibreLane 3.0.5.**
`librelane/steps/openroad.py:400` filters `LAYERS_RC` with
`Filter([corner_wildcard])` and line 407 filters `VIAS_R` with
`Filter(corner_wildcard)` — the bare string. `Filter.__init__` iterates
its argument, so `"max_*"` becomes the five one-character wildcards
`m`, `a`, `x`, `_`, `*`, and the `*` then matches every corner:

```
$ .venv-flow/bin/python -c "from librelane.common.misc import Filter; \
    print(list(Filter('max_*').filter(['nom_tt_025C_1v80','max_ss_100C_1v60'])))"
['nom_tt_025C_1v80', 'max_ss_100C_1v60']
```

**[fact]**. This is upstream, not configuration. It is why section 8's
`VIAS_R` is applied under `"*"` with the `nom` values rather than per
corner, and why the nom-to-max via spread — `mcon` 9.30 to 23.0, `via`
4.50 to 15.0 — stays unmodelled. Section 8.2's result makes that
limitation immaterial to the conclusion, since the term it would sharpen
is the one that does not move. Worth an upstream issue.
